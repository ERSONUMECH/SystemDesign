START HEREWhat system design actually is

Every system design question is the same question in disguise: given a set of requirements and a budget, what do you build, and what breaks first when it grows?

The field splits into two layers that use completely different vocabularies.

High-level design (HLD)Low-level design (LLD)
QuestionHow do the boxes talk to each other?What lives inside one box?
Unit of thoughtService, database, queue, cacheClass, interface, method
ConcernsScale, latency, availability, cost, consistencyExtensibility, readability, correctness, testability
ArtifactsArchitecture diagram, API contract, data model, capacity planClass diagram, sequence diagram, interfaces, state machine
Fails whenTraffic grows 100×Requirements change slightly
Typical prompt"Design Twitter""Design a parking lot"

They are not independent. An HLD that says "notification service" is a promise that somebody can write the LLD for it. An LLD that hard-codes a single database is a promise the HLD can never shard. Good engineers move between the two layers constantly.

The three forces

Almost every decision in this document is a trade between three things:

  • Latency — how long one request takes. Reduced by moving data closer (caches, CDNs, replicas, denormalization).
  • Consistency — whether everybody sees the same data. Reduced by every technique that improves latency.
  • Cost — machines, bandwidth, and engineer-hours. Reduced by doing less.

When you cannot decide between two designs, you have not yet decided which of these you are willing to give up. Say so out loud, pick one, and move on.

PART 1 · HIGH-LEVEL DESIGN1. Fundamentals and vocabulary

1.1 Scalability

DEFINITION

System design is the process of defining the architecture, components, interfaces, and data of a system to satisfy specified functional and non-functional requirements — chiefly scale, latency, availability, consistency, and cost.

A system is scalable if you can handle more load by adding resources, without redesigning it.

  • Vertical scaling (scale up) — bigger machine. Simple, no code changes, no distributed-systems problems. Hard ceiling, single point of failure, price grows faster than capacity. Correct answer far more often than interview candidates admit.
  • Horizontal scaling (scale out) — more machines. Effectively unbounded, tolerates machine death. Forces you to solve state: sessions, coordination, data partitioning, consistency.

The practical rule: scale vertically until it hurts, scale horizontally forever after. The transition point is where you must make services stateless so any machine can serve any request.

1.2 Latency, throughput, and percentiles

  • Latency — time for one operation. Throughput — operations per second. They are not inverses; batching raises both throughput and latency.
  • Never quote an average latency. Averages hide the tail. Quote p50 / p95 / p99 / p99.9.
  • Tail amplification: if a page fans out to 100 services each with a 1% chance of being slow, roughly 63% of pages hit at least one slow service. Your p99 becomes everyone's median. Fixes: hedged requests, fan-out reduction, per-service timeouts.

1.3 Availability and reliability

Availability = fraction of time the system serves requests correctly. Reliability = probability it works over a window. Fault tolerance = continuing to work while components are broken. Durability = data written stays written.

"Nines"AvailabilityDowntime / yearDowntime / month

Three99.9%8.77 hours43.8 min

Components in series multiply availability (0.99 × 0.99 = 0.98) — every dependency makes you worse. Components in parallel with failover compound the failure probability instead (1 − 0.01² = 0.9999) — redundancy makes you better. This is why you remove dependencies from the critical path and duplicate the ones you cannot remove.

SLI, SLO, SLA

  • SLI — the measurement ("p99 latency of /checkout").
  • SLO — the internal target ("p99 < 300 ms, 99.9% of the month").
  • SLA — the contract with a customer, with money attached. Always looser than the SLO.
  • Error budget = 1 − SLO. A 99.9% SLO buys 43 minutes of failure per month. Spend it on releases; when it is gone, stop shipping and fix reliability.

1.4 Single points of failure

Walk the request path and ask at every hop: if this one thing dies, does the product stop? Every "yes" is an SPOF. The standard removals are redundancy (N+1 instances), failover (standby promoted on health-check failure), and isolation (blast radius limited to one cell, shard, or region).

1.5 Statelessness

A stateless service keeps no request-specific memory between calls; all state lives in a database, cache, or the request itself (e.g. a signed token). This is what makes horizontal scaling, autoscaling, rolling deploys, and instance death cheap. When you hear "sticky sessions," treat it as technical debt you accepted.

1.6 Push vs pull

  • Pull — client asks. Simple, wasteful, and stale by half a poll interval.
  • Push — server sends. Efficient and fresh, but needs connection state, and you must handle slow consumers (backpressure).
  • Most large systems are hybrid: push for the common case, pull as the reconciling fallback (e.g. push a "new messages" signal, pull the actual messages).

2. Back-of-the-envelope estimation

DEFINITION

Capacity estimation (“back-of-the-envelope”) is the practice of deriving order-of-magnitude figures for traffic, storage, memory, and bandwidth from stated or assumed usage numbers, in order to choose an architecture before writing any code.

The point of estimation is not accuracy. It is to discover, in two minutes, whether you need one machine or one thousand — because those are different designs.

2.3 The estimation recipe

  1. Users. Total users → daily active users (DAU). A common assumption: DAU is 10–30% of registered users.
  2. QPS. QPS = DAU × actions per user per day ÷ 86,400. Round 86,400 to 10⁵.
  3. Peak QPS. Multiply average by 2–5×. Say which multiplier you chose.
  4. Read:write ratio. Usually the single most design-relevant number. 100:1 means "cache everything"; 1:1 means "the write path is the problem".
  5. Storage. writes per day × bytes per record × retention days × replication factor. Add ~30% for indexes and overhead.
  6. Bandwidth. QPS × average payload size, in and out separately.
  7. Memory for cache. Apply the 80/20 rule: cache the 20% of data serving 80% of reads.
  8. Machines. Assume a commodity box handles ~1,000 QPS of application work and holds ~64–256 GB RAM. Divide.

Worked example — a Twitter-like feed

Assumptions
  300M MAU, 50% DAU          -> 150M DAU
  Each user posts 2 tweets/day -> 300M writes/day
  Each user reads 100 tweets/day -> 15B reads/day

WHAT THIS BOUGHT US

Two minutes of arithmetic produced four design decisions: reads dominate so precompute feeds; media dwarfs text so store it separately behind a CDN; the hot set fits in RAM so cache aggressively; and 810 TB does not fit on one machine so the tweet store must be sharded.

DEFINITION

A network protocol is an agreed set of rules for how two endpoints format, transmit, and interpret data. An API is the contract a service exposes to its callers: which operations exist, what they require, and what they return.

3.2 DNS

Hierarchical lookup: root → TLD → authoritative nameserver, with caching at every level governed by TTL. Useful in design because DNS is also a crude load balancer and failover mechanism.

  • Round-robin DNS — multiple A records, client picks. Free, no health checks, TTL-limited failover.
  • GeoDNS / latency-based routing — return the nearest region's IP.
  • Anycast — one IP announced from many locations; the network routes to the closest. Used by CDNs and DNS providers.
  • Low TTLs make failover fast and lookups expensive. 30–60 s is a common compromise.

REST conventions worth stating

  • Nouns, not verbs: POST /users/42/orders, not /createOrder.
  • Idempotency: GET, PUT, DELETE are idempotent; POST is not. Make POST idempotent with a client-supplied Idempotency-Key header stored server-side.
  • Safe: GET/HEAD must not mutate. Anything else breaks caches and crawlers.
  • Versioning: URL path (/v2/) for breaking changes; additive fields never break.
  • Pagination: prefer cursor-based (?after=opaque_token&limit=20) over offset. Offset is O(n) deep in the table and skips or duplicates rows when the underlying data shifts.
  • Status codes: 200 ok, 201 created, 202 accepted (async), 400 bad input, 401 unauthenticated, 403 unauthorized, 404 missing, 409 conflict, 422 semantic error, 429 rate-limited, 500 server bug, 503 overloaded (send Retry-After).

4. Load balancing

DEFINITION

A load balancer is a component that distributes incoming requests across multiple backend instances, so that no single instance is overwhelmed and the failure of one instance does not take down the service.

4.1 Layer 4 vs layer 7

L4 (transport)L7 (application)
SeesIP + portURL, headers, cookies, body
Can doForward packets fastRoute by path, terminate TLS, rewrite, compress, authenticate, rate limit
CostVery low latency, huge throughputMore CPU, must decrypt
ExamplesAWS NLB, IPVSNGINX, Envoy, HAProxy, AWS ALB

4.2 Algorithms

  • Round robin — even rotation. Ignores that requests differ in cost.
  • Weighted round robin — for heterogeneous machines.
  • Least connections — send to the least busy. Better with long-lived or variable requests.
  • Least response time — connections plus measured latency.
  • IP hash / consistent hash — same client (or key) to the same server. Needed for cache locality and sticky sessions.
  • Power of two choices — pick two servers at random, send to the less loaded. Nearly as good as global least-connections with almost no coordination. Quietly the best default at scale.

4.3 Health checks and failover

Passive checks observe real traffic for errors; active checks hit /healthz on a timer. Distinguish liveness (should I restart this?) from readiness (should I send it traffic?). A deep health check that queries the database can cause a total outage when the database blips, because every instance is marked unhealthy at once — check dependencies shallowly and shed load instead.

The LB itself must not be an SPOF: run an active-passive pair with a floating virtual IP, or use a managed/anycast LB.

5. Caching and CDNs

Caching is the highest-leverage move in system design and the largest source of correctness bugs. Every cache is a copy of the truth that is allowed to be wrong.

5.1 Where caches live

  1. Client — browser cache, app local store. Free, but you cannot invalidate it.
  2. CDN / edge — static assets and cacheable API responses near the user.
  3. Reverse proxy — full-page or fragment caching at the LB.
  4. Application in-process — nanosecond access, but N copies with N different states.
  5. Distributed cache — Redis or Memcached. One shared truth, ~0.5 ms away.
  6. Database — buffer pool, query cache, materialized views.

5.2 Read patterns

PatternMechanicsNotes
Cache-aside (lazy loading)App checks cache; on miss reads DB and populates cacheThe default. Only requested data is cached. Every miss costs a DB hit; stale data possible until TTL
Read-throughCache itself loads from DB on missCleaner app code; requires cache-provider support

5.3 Write patterns

PatternMechanicsTrade-off
Write-throughWrite cache and DB synchronouslyCache always fresh; every write pays two latencies; caches data never read
Write-aroundWrite DB only; cache fills on readAvoids polluting cache with write-only data; first read is a miss
Write-back (write-behind)Write cache, flush to DB asynchronouslyFastest writes, absorbs spikes; data loss if cache dies before flush

5.4 Eviction and invalidation

Eviction policies: LRU (default, good general locality), LFU (better for stable hot sets, needs aging), FIFO, Random (surprisingly competitive and cheap), TTL (always set one, even a long one).

Invalidation strategies, in increasing order of difficulty: TTL expiry; explicit delete-on-write; versioned keys (user:42:v7) which makes invalidation a write to a version counter; and change-data-capture streams that invalidate from the database's replication log.

5.5 The four classic cache failures

  • Thundering herd / stampede — a hot key expires and 10,000 requests hit the database simultaneously. Fix: a per-key lock so one request repopulates while others wait or serve stale; or probabilistic early expiry; or background refresh-ahead.
  • Cache penetration — requests for keys that do not exist anywhere bypass the cache every time (often an attack). Fix: cache the negative result with a short TTL, and/or a Bloom filter of existing keys in front.
  • Cache avalanche — many keys expire at the same instant (they were all loaded at the same instant). Fix: add random jitter to every TTL.
  • Hot key — one celebrity key saturates a single cache node. Fix: replicate that key across nodes with suffixed names, or add a local in-process cache for the top-N keys.

5.7 CDN

Geographically distributed edge caches for static and cacheable dynamic content. Benefits: latency (content is physically near), origin offload, and absorption of traffic spikes and DDoS.

  • Push CDN — you upload content in advance. Good for small, stable catalogs.
  • Pull CDN — the edge fetches from origin on first miss. Good for large or changing catalogs. The default.
  • Control with Cache-Control: max-age, s-maxage, stale-while-revalidate, ETag, and Vary.
  • Cache busting: never invalidate; instead, put a content hash in the filename (app.9f2c1a.js) and cache it for a year.
  • Watch for: cost per GB egress, thundering herd at the origin on mass expiry (use tiered/shield caching), and never caching personalized responses at a shared edge.

HOW TO ANSWER "SQL OR NOSQL?"

Not by reciting properties. Answer with the access pattern. "The dominant query is 'fetch one user's last 50 messages ordered by time', there are no cross-entity joins, and the write rate is 50k/s — so a wide-column store keyed by (conversation_id, timestamp) fits, and I'll keep billing in Postgres because it needs real transactions." Polyglot persistence is a legitimate answer.

6.2 ACID and transaction isolation

Atomicity (all or nothing), Consistency (invariants preserved), Isolation (concurrent transactions do not corrupt each other), Durability (committed survives a crash). The counterpart for many NoSQL stores is BASE: Basically Available, Soft state, Eventual consistency.

Concurrency control: pessimistic locking (take a lock, others wait — good under high contention, risks deadlock) vs optimistic (read a version number, check it at write time, retry on mismatch — good under low contention, no locks held).

6.3 Indexing

  • B+ tree — the relational default. Balanced, O(log n) point lookups, excellent range scans, sorted order. Read-optimized; each write must update the tree in place.
  • LSM tree — used by Cassandra, RocksDB, and friends. Writes go to an in-memory memtable, then flush to immutable sorted files, merged by background compaction. Write-optimized; reads may touch several files (mitigated by Bloom filters), and compaction costs I/O.
  • Hash index — O(1) equality, no ranges.
  • Composite index — obeys the leftmost-prefix rule: an index on (a,b,c) serves queries on a, a,b, a,b,c, not on b alone.
  • Covering index — includes every column the query needs, so the base table is never read.
  • Costs: every index slows writes and consumes space. Index for your real queries, not speculatively.

6.4 Normalization vs denormalization

Normal forms remove redundancy (1NF atomic values; 2NF no partial dependency on a composite key; 3NF no transitive dependency). Normalized schemas make writes cheap and correct, and reads expensive (joins).

Denormalization duplicates data to remove joins from the read path. It is the standard move once reads dominate — and it makes every write a multi-place update, so you need either transactions, an async reconciliation job, or an acceptance that copies can lag. In NoSQL, this is not a hack: you model the table around the query.

6.5 Other things that matter

  • Connection pooling — databases die from connection count long before they die from query load. Use PgBouncer or equivalent.
  • N+1 queries — the most common real-world performance bug. Batch or join.
  • Materialized views — precomputed query results, refreshed on a schedule or by trigger.
  • OLTP vs OLAP — transactional row stores for the product; columnar warehouses (Snowflake, BigQuery, ClickHouse, Redshift) for analytics. Never run analytics on the primary.
  • Soft deletes and append-only tables preserve history and make debugging possible.

7. Replication

DEFINITION

Replication is storing the same data on multiple nodes so the system survives node failure and can serve reads from more than one place. It answers “what if this copy dies?” — the companion question to partitioning, “what if this copy is too big?”

Copies of the same data on multiple nodes, for read scaling, availability, and geographic locality.

7.1 Topologies

  • Single-leader — all writes to the leader, reads from followers. Simple, no write conflicts. The leader is a write bottleneck and a failure point; failover needs leader election.
  • Multi-leader — writes accepted in several regions and replicated between them. Great write availability and local latency; you must resolve write conflicts.
  • Leaderless (Dynamo-style) — the client writes to several nodes and reads from several. Uses quorums, read repair, and anti-entropy. Cassandra and DynamoDB work this way.

7.2 Synchronous vs asynchronous

7.3 Replication lag and how to live with it

Asynchronous followers are behind. Three anomalies and their fixes:

  • Read-your-own-writes — a user posts a comment and does not see it. Fix: route that user's reads to the leader for a few seconds, or track a write timestamp/LSN in the session and only read from a replica that has caught up.
  • Monotonic reads — a user sees data, refreshes, and sees it vanish (two replicas at different positions). Fix: pin a user to one replica by hashing their ID.
  • Consistent prefix reads — causally related writes arrive out of order. Fix: route causally related writes to the same partition, or carry causal metadata.

7.4 Failover

Detect (missed heartbeats), elect (consensus or an external coordinator), promote, and redirect. The dangers are split brain (two nodes believe they are leader — solved with fencing tokens and quorum) and silent data loss (unreplicated writes on the old leader are discarded when it rejoins).

8. Partitioning and sharding

DEFINITION

Partitioning (sharding) is splitting one logical dataset across multiple nodes so that no single node holds all of it, so both storage capacity and write throughput scale with the number of nodes.

Splitting one dataset across nodes so that no node holds it all. Replication copies; partitioning divides. Real systems do both: each shard is replicated.

Ring of 2^32 positions.

  - hash each KEY onto the ring

Used by: Cassandra, DynamoDB, Riak, Memcached clients, and every CDN's request routing.

8.3 Choosing a shard key

The most consequential decision in the design. A good key has high cardinality, even access distribution, and matches the dominant query so that one query hits one shard.

  • Hotspot / celebrity problem — sharding by user_id puts a 200-million-follower account on one node. Fixes: a compound key with a salt (user_id:bucket), a separate path for celebrities, or dedicated caching for the hot entity.
  • Cross-shard queries — anything not keyed by the shard key must scatter-gather across all shards and merge. Slow, and as available as the least available shard. Solve with a secondary index service, a denormalized read model, or a search cluster.
  • Cross-shard transactions — avoid. Redesign so a transaction lives inside one shard, or accept sagas.
  • Resharding — plan for it from day one. Simplest trick: start with many more logical shards than physical nodes (e.g. 1024 logical shards on 8 machines) and move logical shards around. Otherwise: double-write to old and new, backfill, verify, cut over, clean up.

9. CAP, PACELC, and consistency models

DEFINITION

Consistency (in the distributed-systems sense) is a guarantee about what value a read can return relative to prior writes. Strong consistency guarantees the latest write; eventual consistency only guarantees that, absent new writes, replicas will eventually agree.

9.1 CAP, stated correctly

In the presence of a network partition, a distributed system must choose between consistency (every read sees the latest write, or an error) and availability (every request gets a non-error response, possibly stale). You do not "pick two of three" — partitions are not optional, so you are choosing between CP and AP, and only during a partition.

  • CP — refuse to serve rather than serve wrong. Banking, inventory, locks. HBase, ZooKeeper, etcd, Spanner.
  • AP — serve possibly-stale data rather than nothing. Feeds, catalogs, DNS, shopping carts. Cassandra, DynamoDB, Riak.

9.2 PACELC — the more useful version

If there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. This is better because it names the trade you make 99.99% of the time: synchronous cross-region replication costs latency on every single write, partition or not.

9.3 Consistency models, strongest to weakest

  1. Linearizable / strong — the system behaves as if there were one copy and operations happened instantaneously in real-time order. Expensive; requires consensus.
  2. Sequential — all nodes see operations in the same order, not necessarily real time.
  3. Causal — causally related operations are seen in order everywhere; concurrent ones may differ. The sweet spot for many products (a reply never appears before its parent).
  4. Read-your-writes / monotonic reads / monotonic writes — session guarantees. Cheap and usually what users actually notice.
  5. Eventual — stop writing and eventually all replicas converge. No promise about when.

9.4 Quorums

N = replicas, W = nodes that must ack a write, R = nodes read from

W + R > N   ->  read and write sets overlap -> reads see the latest write
W = N, R = 1 ->  fast reads, slow/fragile writes
W = 1, R = N ->  fast writes, slow reads
N=3, W=2, R=2 -> the common balanced choice; tolerates one node down

Quorum overlap gives strong-ish consistency without a leader, but does not by itself give linearizability (concurrent writes, partial failures, and sloppy quorums all leak).

9.5 Resolving conflicts

  • Last-write-wins by timestamp — trivial, and silently discards data. Needs synchronized clocks you do not have.
  • Version vectors / vector clocks — detect that two writes were concurrent rather than ordered, then hand both to the application to merge (Dynamo's "siblings").
  • CRDTs — data types (counters, sets, sequences) that merge deterministically by construction. The basis of collaborative editors.
  • Application merge — union the shopping carts; the user deletes what they do not want. Amazon's original answer.

10. Coordination, consensus, and distributed transactions

DEFINITION

Consensus is the problem of getting a group of nodes to agree on a single value despite some nodes crashing or messages being delayed, in a way that every non-faulty node eventually agrees and no two nodes disagree.

10.1 Consensus

Getting a group of nodes to agree on one value despite crashes and network delay. Paxos is the classic; Raft is the one people implement, because it decomposes into leader election, log replication, and safety. Both require a majority quorum, which means consensus clusters have an odd number of nodes (3, 5, 7) and tolerate ⌊(n−1)/2⌋ failures.

You rarely implement consensus. You use it, via ZooKeeper, etcd, or Consul, for: leader election, configuration that must be globally agreed, service registries, and distributed locks.

10.2 Distributed locks — and why they are dangerous

A lock in Redis (SET key value NX PX 30000) is easy and subtly wrong: the holder can pause for a GC cycle past the TTL while another client takes the lock, and now two clients act as owner. The fix is a fencing token — a monotonically increasing number issued with the lock, which the downstream resource checks and rejects if it has already seen a higher one.

10.3 Distributed transactions

  • Two-phase commit (2PC) — a coordinator asks all participants to prepare, then tells them to commit. Correct, and blocking: if the coordinator dies after prepare, participants hold locks indefinitely. Avoid across services.
  • Saga — model the transaction as a sequence of local transactions, each with a compensating action to undo it. Two flavours: choreography (services react to each other's events; no central logic, hard to follow) and orchestration (a coordinator drives the steps; explicit and debuggable).
  • Transactional outbox — the standard fix for "write to the database AND publish an event" atomically. Write the event to an outbox table in the same local transaction as the business data; a separate relay reads the table (or the DB's change log) and publishes. Solves the dual-write problem.
  • Idempotency — because at-least-once delivery means every consumer sees duplicates. Give each operation a unique key, record processed keys, and make the operation safe to repeat. This is not optional; it is the price of any retry.

10.4 Time and ordering

Wall clocks on different machines disagree by milliseconds and occasionally jump backwards (NTP correction, leap seconds). Never order distributed events by System.currentTimeMillis(). Use logical clocks (Lamport timestamps for a total order, vector clocks to detect concurrency), or a bounded-uncertainty clock like Spanner's TrueTime, or a central sequencer.

11. Messaging and asynchronous processing

DEFINITION

A message queue decouples a producer from a consumer by holding messages until they are processed. A distributed log additionally retains messages after consumption, so multiple independent consumers can each read the same stream at their own pace.

The single most useful architectural move: take work off the request path. If the user does not need the result to render the response, it belongs in a queue.

11.1 Why

  • Decoupling — producer and consumer deploy, scale, and fail independently.
  • Load levelling — a spike fills the queue instead of melting the database.
  • Retries — a failed job stays in the queue; a failed HTTP call is gone.
  • Fan-out — one event, many independent consumers.

11.2 Queue vs log

11.3 Delivery semantics

  • At-most-once — fire and forget. Fast, loses messages.
  • At-least-once — ack after processing, redeliver on failure. The practical default; guarantees duplicates.
  • Exactly-once — not achievable end-to-end in general; achieved in practice as at-least-once delivery + idempotent consumers, or within one system via transactional offsets.

11.4 Operating a queue

  • Dead-letter queue — after N failed attempts, park the message for inspection rather than looping forever.
  • Backpressure — when consumers fall behind: scale consumers, shed low-priority work, or slow producers. Monitor consumer lag — it is the single best health metric for an async system.
  • Poison messages — one malformed message blocking a partition. DLQ it.
  • Ordering — you only get it per partition, so partition by the key whose order matters (e.g. user_id), and accept that global order does not exist.
  • Priority — usually cleaner as separate queues than as a priority field.

11.5 Event-driven patterns

  • Pub/sub — publishers emit to topics; subscribers receive independently.
  • Event sourcing — the log of events is the source of truth; current state is a fold over the log. Gives perfect audit and time-travel; costs you easy queries and schema evolution pain.
  • CQRS — separate the write model from one or more read models, each shaped for its query and updated asynchronously. Pairs naturally with event sourcing, and independently with any read-heavy system.
  • Change data capture (CDC) — stream the database's replication log (Debezium) into Kafka to keep caches, search indexes, and warehouses in sync without dual writes.

Where: at the edge/gateway (protects everything), per service (protects that service). Keys: user, API key, IP, endpoint, or tenant. State lives in Redis so all gateway instances share counters; respond with 429 plus X-RateLimit-Remaining and Retry-After.

13.2 Failure-handling patterns

  • Timeout — every network call needs one. No timeout means a slow dependency consumes all your threads.
  • Retry with exponential backoff and jitter — delay = min(cap, base × 2^attempt) × random(). Without jitter, all clients retry in lockstep and you have built a self-inflicted DDoS. Only retry idempotent operations, and cap the attempts.
  • Circuit breaker — CLOSED (normal) → OPEN (fail fast without calling) after an error threshold → HALF-OPEN (let a trickle through to test recovery) → CLOSED. Stops you from hammering a dying dependency and gives it room to recover.
  • Bulkhead — separate thread pools or connection pools per dependency, so one slow downstream cannot exhaust the resources needed for everything else.
  • Graceful degradation — serve the page without the recommendations widget. Decide in advance which features are droppable.
  • Load shedding — reject the excess early with 429/503 rather than letting queues grow and every request time out. A system that serves 70% of traffic well beats one that serves 100% of traffic past the timeout.
  • Backpressure — propagate "slow down" upstream instead of buffering without limit.
  • Chaos engineering — deliberately kill instances and inject latency in production to verify that all of the above actually work.

13.3 Multi-region

  • Active-passive — one region serves, another stands by with replicated data. Simple; the standby is expensive and untested unless you drill.
  • Active-active — all regions serve. Best latency and availability; you now own multi-leader write conflicts and data-residency rules.
  • Define RPO (how much data you can lose) and RTO (how long you can be down). They determine the design and the bill.

14.1 Inverted index

Operationally: shard the index by document, replicate each shard, query all shards and merge (scatter-gather). Keep the search cluster in sync with the primary database via CDC, never by dual writes. Elasticsearch is the default; accept that it is a derived store, not a source of truth.

14.2 Blob / object storage

  • Store media in S3-style object storage, and only the URL and metadata in your database. Never put images in a relational table.
  • Presigned URLs let clients upload directly to the bucket, keeping large bodies off your application servers entirely.
  • Multipart upload for large files: chunk, upload in parallel, resume failed chunks, assemble server-side.
  • Storage tiers — hot / infrequent / archive, with lifecycle rules. Serve everything through a CDN.
  • Deduplication — hash the content; identical files stored once (this is how Dropbox saves most of its space).
  • Chunking + delta sync — split files into fixed or content-defined chunks so an edit re-uploads only the changed chunks.

15. Observability

Monitoring tells you that something is wrong. Observability lets you ask why without shipping new code.

  • Metrics — numeric time series, cheap and aggregatable, no per-request detail. Counters, gauges, histograms. Prometheus, Grafana.
  • Logs — discrete events. Make them structured (JSON) with a correlation ID on every line. Sample aggressively at high volume.
  • Traces — one request's path across services as a tree of spans, propagated by trace context headers. The only tool that finds "which of these 30 services is the slow one". OpenTelemetry, Jaeger.

What to measure

  • RED (per service): Rate, Errors, Duration.
  • USE (per resource): Utilization, Saturation, Errors.
  • Four golden signals: latency, traffic, errors, saturation.

Alert on symptoms users feel (error rate, p99 latency, queue lag), not on causes (CPU at 80% is not an incident). Every alert should be actionable and have a runbook; a noisy alert is worse than no alert. Run blameless postmortems.

16. Security

DEFINITION

Authentication establishes who is making a request. Authorization decides what they are allowed to do. Systems routinely conflate the two; keep them as separate checks.

16.1 Authentication and authorization

  • Sessions — server stores session state, client holds an opaque cookie. Easy revocation; needs shared session storage.
  • JWT — signed, self-contained token; stateless verification. Cannot be revoked before expiry, so keep access tokens short-lived (5–15 min) and pair them with a long-lived, revocable refresh token.
  • OAuth 2.0 — delegated authorization (let app X act on my behalf). OIDC is the identity layer on top that gives you authentication.
  • Authorization models — RBAC (roles), ABAC (attributes and policy), ACL (per-object lists). Check authorization on every request at the service, not just in the UI.
  • mTLS for service-to-service identity inside the mesh.

16.2 Data protection

  • In transit: TLS everywhere, including internal hops. At rest: disk/column encryption with a managed KMS and key rotation.
  • Passwords: bcrypt, scrypt, or Argon2 with a per-user salt. Never SHA-256, never unsalted, never reversible.
  • PII: minimize what you collect, tokenize or encrypt what you keep, log none of it, and honour deletion requests (GDPR/CCPA) — which means knowing every store a user's data reaches.

16.3 Common attacks worth naming

  • SQL injection — parameterized queries, always.
  • XSS — escape output, set a Content-Security-Policy.
  • CSRF — SameSite cookies plus anti-CSRF tokens.
  • SSRF — validate and allowlist outbound URLs; block link-local metadata addresses.
  • DDoS — anycast absorption, CDN, WAF, rate limiting, and the ability to shed traffic cheaply at the edge.
  • Insecure direct object reference — /invoice/1234 must check that this user owns 1234.

17. Deployment and operations

DEFINITION

A deployment strategy is the procedure for replacing a running version of software with a new one while controlling the blast radius of anything that goes wrong.

  • Rolling — replace instances in batches. No extra capacity needed; two versions run at once, so changes must be backward compatible.
  • Blue-green — a full second environment, flip the LB, roll back instantly. Doubles infrastructure during the switch.
  • Canary — 1% of traffic to the new version, watch error rate and latency, then ramp. The safest for large systems.
  • Feature flags — decouple deploy from release; enable per user, per cohort, or per percentage, and kill a bad feature without a rollback.
  • Database migrations — always expand-then-contract: add the new column, dual-write, backfill, switch reads, stop writing the old, drop it. Never a single breaking migration in lockstep with a deploy.
  • Infrastructure as code — Terraform/Pulumi; environments should be reproducible, not hand-built.
  • Containers and orchestration — Docker for the artifact, Kubernetes for scheduling, autoscaling (HPA on a real signal like queue depth, not just CPU), and self-healing.
  • Backups — plus, crucially, tested restores. An untested backup is a hope. Know your RPO and RTO.

19. High-level design case studies

Twelve standard problems, each reduced to its central insight and the two or three decisions that actually matter. Everything else in an answer follows the template in Part 3.

19.1 URL shortener

  • Core problem: generate short unique IDs; read-heavy (100:1).
  • ID generation: base62 encode of a distributed counter or Snowflake ID (7 chars of base62 = 3.5 trillion URLs). Alternative: hash the URL and take a prefix, resolving collisions by rehashing — simpler to reason about but needs a uniqueness check.
  • Storage: a KV store keyed by short code. Trivially shardable.
  • Reads: cache aggressively (the distribution is extremely skewed), serve 301 for permanent (browser caches it, you lose analytics) or 302 if you want to count clicks.
  • Extras: custom aliases, expiry and cleanup, analytics via an async event stream, abuse/malware scanning.

19.2 Rate limiter

  • Core problem: shared counters across many gateway instances, with minimal added latency.
  • Design: sliding-window counter in Redis, updated with an atomic Lua script; key is {user}:{endpoint}:{window}.
  • Scale trick: approximate local counting with periodic sync to reduce Redis round trips, accepting slight over-admission.
  • Failure mode: decide explicitly whether the limiter fails open (availability) or closed (protection) when Redis is unreachable.

19.3 News feed / timeline (Twitter, Instagram)

  • Core problem: fan-out. The decision is whether to compute the feed at write time or read time.
  • Fan-out on write (push) — on posting, append the post ID to every follower's precomputed timeline list in Redis. Reads are O(1) and instant. Writing costs O(followers), which is catastrophic for celebrities.
  • Fan-out on read (pull) — on opening the app, query the posts of everyone you follow and merge. Cheap writes, expensive and slow reads.
  • The real answer: hybrid. Push for ordinary users; for accounts above a follower threshold, do not fan out — merge their recent posts into the timeline at read time. This one sentence is what the question is testing.
  • Store timelines as capped lists (most recent ~800 IDs), hydrate post content from cache, and rank asynchronously.

19.4 Chat / messaging (WhatsApp, Slack)

  • Core problem: stateful persistent connections and delivery guarantees.
  • Connections: WebSocket servers behind an L4 LB; a Redis registry maps user_id → gateway_instance; messages route between gateways over a pub/sub bus.
  • Storage: wide-column store keyed by (conversation_id, message_id) where message_id is time-sortable — gives cheap "last N messages" range reads.
  • Semantics: per-conversation sequence numbers for ordering; client-generated message IDs for idempotent retries; sent/delivered/read receipts as separate events; an offline queue with push notifications.
  • Group chat: fan-out per member; large groups get the celebrity treatment again.
  • E2E encryption moves key exchange to clients and makes server-side search impossible — say so.

19.5 Video streaming (YouTube, Netflix)

  • Upload path: presigned direct-to-blob upload → a transcoding pipeline (queue + worker fleet) producing multiple resolutions and bitrates, segmented into ~4–10 s chunks, plus a manifest.
  • Delivery: HLS/DASH adaptive bitrate; the player picks a rendition per segment based on measured bandwidth. Everything served from the CDN; popular titles pre-pushed to edge caches.
  • Metadata: relational or document store; view counts via an async counting pipeline, never a synchronous increment.
  • The real cost centre is bandwidth and storage, so the interesting engineering is codec choice, per-title encoding, and edge cache hit rate.

19.6 Ride hailing (Uber, Lyft)

  • Core problem: continuous geospatial updates and matching.
  • Location: drivers send a ping every few seconds; store current position in an in-memory geospatial index sharded by region (quadtree or geohash / Redis GEO). Persist the track asynchronously.
  • Matching: query the cells covering the rider's radius, rank candidates by ETA (not distance), offer to drivers sequentially with a timeout, and use a lock or state machine so a driver cannot accept two rides.
  • Trip state is a small, explicit state machine — this is where the LLD half of the question lives.
  • Surge pricing is a windowed supply/demand aggregation per cell.

19.7 Web crawler

  • Frontier queue of URLs with politeness (per-domain rate limits and robots.txt) and priority.
  • Bloom filter or hash set for "already seen"; content hashes to detect duplicate pages.
  • Worker fleet fetches, parses, extracts links, stores raw pages in blob storage, pushes text to the indexing pipeline.
  • Traps to mention: infinite calendars and spider traps, DNS load, robots compliance, and re-crawl scheduling by page change rate.

19.8 Notification service

  • One API, many channels (push, SMS, email, in-app), each with its own third-party provider, retry policy, and failure modes.
  • Queue per channel; template service; user preference and quiet-hours service; deduplication and rate caps per user.
  • Idempotency keys so a retried upstream call does not send two SMS messages.
  • Track delivery status via provider webhooks; DLQ everything that exhausts retries.

19.9 File sync / cloud drive (Dropbox, Google Drive)

  • Split files into chunks (4 MB); hash each chunk; upload only chunks the server does not already have — this gives deduplication and delta sync in one mechanism.
  • Metadata service holds the file tree, versions, and chunk lists; chunks live in blob storage.
  • Clients hold a long poll / WebSocket for change notifications, then pull the delta.
  • Conflict handling: version vectors, and when in doubt keep both copies as "conflicted copy" — the honest answer.

19.10 Ticket booking (BookMyShow, airline seats)

  • Core problem: no double-booking under a thundering herd for a small inventory.
  • Two-phase: a short-lived hold/reservation (row-level lock or conditional update with TTL) while the user pays, then confirmation. Expired holds return inventory via a sweeper.
  • This is a CP problem — correctness beats availability. Use transactions on a single shard per event.
  • Queue users at the edge for high-demand on-sales; cache seat maps as read-only and only take locks at the point of hold.

19.11 Payments

  • Idempotency keys on every charge request; a ledger as an append-only double-entry table; never mutate a transaction row.
  • Saga across order, payment, and inventory services with explicit compensations (refund, restock).
  • Exactly-once via at-least-once plus idempotent processing; reconcile against the provider daily.
  • Strong consistency, full audit trail, and PCI scope minimization (tokenize cards; never store PANs).

19.12 Search autocomplete

  • Trie of query prefixes, each node caching its top-k completions so a lookup is one traversal and no sort.
  • Built offline from query logs on a schedule; served from memory, sharded by prefix.
  • Sub-100 ms budget end to end, so: debounce on the client, cache at the edge, and accept that the data is hours stale.

PART 2 · LOW-LEVEL DESIGN20. What low-level design covers

HLD stops at the boundary of a service. LLD starts there: the classes, interfaces, and interactions that make one service correct today and changeable next quarter.

An LLD question — "design a parking lot", "design Splitwise" — is not testing whether you can write code. It tests whether you can turn fuzzy requirements into a set of objects with clear responsibilities, and whether your design survives a follow-up requirement without a rewrite. The interviewer will almost always add one ("now support electric-vehicle charging spots"). Your design's answer to that is the real grade.

What you should produce

  • Clarified requirements and explicit assumptions.
  • Core entities, with their responsibilities in one sentence each.
  • A class diagram: classes, key fields, key methods, relationships.
  • Interfaces at the points where behaviour will vary.
  • A sequence diagram for the main flow, and a state machine if there is a lifecycle.
  • Named design patterns — with the reason, not just the name.
  • Concurrency and edge-case handling.

Composition over inheritance

// rigid: behaviour is fixed at compile time by the type
class FlyingDuck extends Duck { void fly() {...} }
class RubberDuck  extends Duck { void fly() { throw ... } }   // LSP violation

// flexible: behaviour is a collaborator, swappable at runtime
class Duck {
    private FlyBehavior  fly;      // interface
    private QuackBehavior quack;   // interface
    Duck(FlyBehavior f, QuackBehavior q) { this.fly = f; this.quack = q; }
    void performFly()   { fly.fly(); }
    void setFly(FlyBehavior f) { this.fly = f; }   // can change mid-life
}

22. SOLID

DEFINITION

SOLID is a set of five class-design guidelines — Single responsibility, Open/closed, Liskov substitution, Interface segregation, Dependency inversion — aimed at code that tolerates change without cascading edits across the codebase.

S — Single responsibility

A class should have one reason to change. Test: describe the class in one sentence without "and".

// violates: persistence, formatting, and business rules all change for different reasons
class Employee {
    double calculatePay();
    void   save();
    String reportToHtml();
}

// obeys
class Employee { double calculatePay(); }
class EmployeeRepository { void save(Employee e); }
class EmployeeReporter   { String toHtml(Employee e); }

O — Open/closed

Open for extension, closed for modification. Adding a new case should mean adding a class, not editing a switch statement that already works.

// closed to extension: every new shape edits this method
double area(Shape s) {
    if (s instanceof Circle)    return ...;
    if (s instanceof Rectangle) return ...;
}

// open: a new shape is a new class, this code never changes again
interface Shape { double area(); }

L — Liskov substitution

A subtype must be usable anywhere its supertype is, without the caller knowing. Subclasses may not strengthen preconditions, weaken postconditions, or throw new exceptions.

// the classic violation
class Rectangle { void setWidth(int w); void setHeight(int h); }
class Square extends Rectangle {
    void setWidth(int w)  { this.w = this.h = w; }   // surprises every caller
}
// any code doing  r.setWidth(5); r.setHeight(4); assert area == 20  now breaks

I — Interface segregation

No client should be forced to depend on methods it does not use. Many small role interfaces beat one fat one.

interface Worker { void work(); void eat(); }     // a Robot must implement eat()
interface Workable { void work(); }               // better
interface Feedable { void eat(); }

D — Dependency inversion

High-level modules should not depend on low-level modules; both should depend on abstractions. In practice: the business logic defines the interface it needs, and infrastructure implements it.

// concrete dependency: OrderService cannot be tested or re-targeted
class OrderService { private MySqlOrderRepo repo = new MySqlOrderRepo(); }

// inverted: the interface belongs to the domain, the implementation to infrastructure
interface OrderRepository { void save(Order o); Order findById(String id); }
class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; }   // injected
}
THE ONE-LINE SUMMARY

Every letter of SOLID is a different way of saying: isolate the thing that is going to change, put an interface in front of it, and inject it. Say which change you are isolating and the principle stops being a buzzword.

23. Other principles worth naming

DEFINITION

DRY (Don't Repeat Yourself): every piece of knowledge should have one authoritative representation. YAGNI (You Aren't Gonna Need It): build for the requirements you have, not the ones you imagine.

  • DRY — one authoritative representation of each piece of knowledge. Beware the false positive: two pieces of code that look alike but change for different reasons should stay separate.
  • KISS — the simplest design that satisfies the stated requirements.
  • YAGNI — build for the requirements you have. Extensibility points cost complexity; add them where change is likely, not everywhere.
  • Law of Demeter — talk only to immediate collaborators. order.getCustomer().getAddress().getCity() couples you to three classes; ask the order for what you need instead.
  • Separation of concerns — presentation, business rules, and persistence in different layers.
  • Program to an interface, not an implementation.
  • Favour immutability — immutable objects are automatically thread-safe, cacheable, and safe to share. Use value objects for money, dates, coordinates, identifiers.
  • Tell, don't ask — send the object a command rather than pulling out its state and deciding for it. Prevents anemic domain models.
  • GRASP — assign each responsibility to the class that has the information to fulfil it (Information Expert), let the object that creates the data create the object (Creator), and use Controller, Low Coupling, High Cohesion as tie-breakers.

26. Code smells and anti-patterns

DEFINITION

A code smell is a surface indicator — not a bug in itself — that usually points to a deeper design problem, detectable by inspection rather than by a failing test.

  • God object — one class that does everything. Split by responsibility.
  • Anemic domain model — entities with only getters and setters, all logic in "service" classes. Move behaviour next to the data it guards.
  • Long parameter list — introduce a parameter object or a builder.
  • Feature envy — a method that mostly uses another class's data. Move it there.
  • Shotgun surgery — one small change forces edits in ten files. Your responsibilities are scattered.
  • Primitive obsession — String userId, double amountInCents everywhere. Introduce value objects; Money that cannot be added to Distance.
  • Switch on type — polymorphism is the fix, nearly always.
  • Circular dependencies — extract a shared abstraction or invert one direction.
  • Singleton abuse — hidden global state, untestable code, initialization-order bugs.
  • Premature abstraction — an interface with one implementation and no prospect of a second. The opposite failure, and just as common.

27. Concurrency in low-level design

DEFINITION

A race condition occurs when the correctness of a computation depends on the relative timing of concurrent operations. A deadlock occurs when two or more threads each hold a resource the other needs and neither can proceed.

Most LLD problems have a shared-resource question hiding in them: two cars racing for the last parking spot, two users buying the last seat, two threads incrementing a counter. Address it explicitly — it is a common differentiator.

  • Race condition — the outcome depends on thread interleaving. Caused by unsynchronized read-modify-write.
  • Critical section — the code that must run exclusively. Keep it as small as possible.
  • Deadlock — needs all four of: mutual exclusion, hold-and-wait, no preemption, circular wait. Break one — usually by imposing a global lock ordering, or by using timeouts on lock acquisition.
  • Livelock / starvation — threads are active but make no progress, or one thread never gets the lock. Use fair locks or backoff.

Tools, from cheapest to heaviest

  1. Immutability and thread confinement — no shared mutable state, no problem. Always the first choice.
  2. Atomics / CAS — AtomicInteger.incrementAndGet(), lock-free, best for counters and flags.
  3. Concurrent collections — ConcurrentHashMap, BlockingQueue. Prefer these to hand-rolled synchronization.
  4. Locks — synchronized, ReentrantLock, ReadWriteLock (many readers, one writer — ideal for read-heavy caches).
  5. Semaphores — for counting a resource pool (e.g. N free parking spots).
  6. Optimistic versioning — a version field checked on write; retry on conflict. Best under low contention, and the same idea as database OCC.
// producer–consumer, the shape you should be able to write from memory
BlockingQueue<Job> queue = new LinkedBlockingQueue<>(1000);   // bounded = backpressure

// producer
queue.put(job);        // blocks when full

// consumer (N threads)
while (running) {
    Job job = queue.take();     // blocks when empty
    process(job);
}

28. The LLD method, step by step

DEFINITION

A variation point is any place in a design where behaviour is expected to change or multiply over time — the location where an interface belongs, so a new case becomes a new class rather than an edit to existing code.

  1. Clarify requirements (3–5 min). Functional: what can each actor do? Non-functional: concurrency, scale, persistence, extensibility. Write down the assumptions you are making and say them aloud.
  2. Identify entities. Underline the nouns in the requirements. Nouns become candidate classes; verbs become methods. Discard nouns that are attributes, not objects.
  3. Assign responsibilities. One sentence per class. If the sentence needs "and", split it.
  4. Define relationships and multiplicity. Who owns whom? Composition or aggregation? One or many?
  5. Find the variation points. Ask: which of these will there be more kinds of next year? Pricing rules, vehicle types, notification channels, payment methods. Put an interface at each one. This is where patterns get chosen, and the choice is now justified rather than decorative.
  6. Sketch the class diagram. Fields and key methods only — not every getter.
  7. Walk the main flow as a sequence diagram. This finds missing methods faster than staring at the class diagram.
  8. Model lifecycles as state machines where they exist.
  9. Handle concurrency and edge cases. Empty, full, duplicate, concurrent, failure mid-way, invalid transition.
  10. Sanity-check extensibility. Ask yourself the interviewer's follow-up before they do, and show where the new class would slot in.
THE MOST COMMON MISTAKE

Jumping straight to classes and then defending them. Spend the first minutes on requirements and the variation points. A design that anticipates the right axis of change beats a more detailed design that anticipates the wrong one.

30. Worked example — parking lot

The canonical LLD question, done the way the method in section 28 prescribes.

Step 1 — Requirements and assumptions

  • Multi-floor lot; spot types: motorcycle, compact, large, electric, handicapped.
  • Vehicle enters at a gate, gets a ticket with entry time and assigned spot; exits at a gate, pays, leaves.
  • Pricing varies by vehicle type and duration; must support future schemes (weekend rates, flat rate for events).
  • Display boards show free spots per floor per type.
  • Multiple entrances operate concurrently — no two vehicles may be given the same spot.
  • Assumed out of scope: reservations, monthly passes, license-plate recognition. (Say this out loud.)

Step 2 — Entities and responsibilities

Step 3 — Variation points

Three things will change: pricing schemes, spot-assignment rules (nearest to lift? nearest to exit? EV first?), and payment methods. Each gets an interface. Spot and vehicle types will also grow, so creation goes through a factory and behaviour is data-driven rather than subclass-per-type.

Step 4 — Class sketch

    boolean fits(Vehicle v) { return SpotCompatibility.allows(type, v.type()); }

    private final List<ParkingFloor> floors;
    private final SpotAssignmentStrategy assigner;
    private final PricingStrategy pricing;
    private final List<AvailabilityListener> listeners;   // Observer

    Ticket park(Vehicle v) {
        ParkingSpot spot = assigner.assign(floors, v)
              .orElseThrow(() -> new LotFullException(v.type()));
        if (!spot.assign(v)) return park(v);      // lost the race, retry
        notifyListeners();
        return ticketService.issue(v, spot);
    }

    Receipt unpark(Ticket t, PaymentMethod method) {
        t.close(Instant.now());
        Money due = pricing.price(t);
        PaymentResult r = method.pay(due);
        if (!r.succeeded()) throw new PaymentFailedException(r);

Step 5 — Concurrency

Two gates can pick the same free spot. The fix in the sketch is that ParkingSpot.assign() is the single atomic point of truth: the strategy may propose a spot, but only the spot itself can grant it, and a loser simply retries. For a distributed version, replace the synchronized block with a conditional update in the database (UPDATE spot SET occupied=true WHERE id=? AND occupied=false) and check the affected row count.

Step 6 — The follow-up

"Now add electric charging spots with per-kWh billing." Nothing in ParkingLot, Ticket, or the gates changes: add an ELECTRIC spot type, a compatibility rule, and an ElectricPricing implementation of PricingStrategy. That is the answer the question was looking for all along.

32.2 MapReduce, in one paragraph

Split the input across machines; each mapper emits key–value pairs; the framework shuffles so all values for a key land on one machine; each reducer aggregates them. The shuffle is the expensive part and the reason data skew — one key with 90% of the values — ruins a job. Spark keeps the same model but holds intermediate results in memory and builds a DAG of stages instead of writing to disk between every step, which is why it is roughly an order of magnitude faster for iterative work.

32.3 Where the data lives

  • Data lake — raw files in object storage (Parquet, ORC), schema applied on read. Cheap, keeps everything, easy to make a mess of.
  • Data warehouse — columnar, modelled, query-optimized (Snowflake, BigQuery, Redshift). Schema on write.
  • Lakehouse — table formats (Iceberg, Delta, Hudi) that add ACID transactions, schema evolution, and time travel on top of lake files.
  • ETL vs ELT — transform before loading (classic, controlled) vs load raw and transform inside the warehouse (modern, flexible, cheaper compute).
  • Columnar storage matters because analytics reads three columns out of two hundred: column layout plus compression means you read 2% of the bytes.

32.4 Idempotent pipelines

Every pipeline gets rerun — after a bug, an outage, or a late-arriving file. Design each step so rerunning it produces the same result: partition outputs by date, write to a temporary location and atomically swap, use deterministic keys, and prefer upserts to appends. A pipeline you cannot safely rerun is a pipeline you cannot fix.

33. Serialization, schemas, and compression

DEFINITION

Serialization is converting an in-memory object into a byte sequence for storage or transmission; deserialization reverses it. A schema is the contract describing that byte sequence's shape.

Schema evolution — the rules that keep a deploy from breaking

  • Backward compatible — new code can read old data. Required whenever you deploy readers first.
  • Forward compatible — old code can read new data. Required whenever producers deploy first, which in a large system is always.
  • Safe changes: add an optional field with a default; add an enum value only if consumers handle unknowns; deprecate rather than delete.
  • Unsafe: renaming a field, changing its type, reusing a field number, making an optional field required.
  • Keep the field numbers, never the field names, as the contract — this is why protobuf numbers fields.

Compression

  • Snappy / LZ4 — fast, moderate ratio. Default for intra-cluster traffic and LSM storage.
  • gzip — slower, better ratio. Fine for HTTP responses.
  • zstd — tunable, usually beats gzip on both axes. The modern default.
  • Brotli — best for static web assets, precompressed at build time.
  • Compress at the edge for bandwidth; compress at rest for storage cost; never compress data you will need to seek into randomly without a block-based format.

34. Distributed file and object storage

DEFINITION

Erasure coding splits data into k fragments and computes m parity fragments, so any k of the k+m total fragments reconstruct the original — durability similar to replication at a fraction of the storage overhead.

  • GFS / HDFS model — one metadata master holding the file→chunk map, many chunk servers holding fixed-size chunks (64–128 MB) replicated three times. Clients ask the master where a chunk is, then talk to chunk servers directly, so the master never touches the data path. Large chunks exist to keep the metadata small enough for memory.
  • Replication vs erasure coding — 3× replication costs 200% overhead and gives simple, fast recovery. Erasure coding (e.g. Reed–Solomon 6+3) costs ~50% overhead for similar durability, but reconstruction is CPU- and network-heavy. Rule: replicate hot data, erasure-code cold data. This is roughly what storage tiers are.
  • Object store semantics — flat keyspace, immutable objects, eventual or strong read-after-write consistency, no rename (a rename is a copy plus delete), no partial update. Design around that rather than treating it as a filesystem.
  • Durability arithmetic — "eleven nines" comes from many independent replicas across failure domains plus continuous background integrity checks, not from any one disk being good.

35. Proxies, edge, and cluster membership

DEFINITION

A proxy is an intermediary that forwards requests on behalf of a client or a server. A forward proxy represents clients to the outside world; a reverse proxy represents servers to the outside world.

35.1 Proxy types

  • Forward proxy — sits in front of clients. Egress control, corporate filtering, anonymity, shared outbound cache.
  • Reverse proxy — sits in front of servers. TLS termination, load balancing, caching, compression, request routing, hiding the topology. Every API gateway is one.
  • WAF — a reverse proxy that inspects payloads for injection, bot patterns, and known exploits.
  • Sidecar proxy — one per service instance, giving you retries, mTLS, and telemetry without touching application code.

35.2 Edge computing

Running code at CDN points of presence: auth checks, A/B routing, personalization, redirects, image resizing. You gain tens of milliseconds and origin offload; you give up long-running work, large dependencies, and easy access to your database. Useful mental model: the edge is for decisions, not for data.

35.3 Peer-to-peer

  • WebRTC — direct browser-to-browser media. Needs STUN to discover public addresses and TURN to relay when NAT traversal fails. A signalling server still brokers the introduction, so "peer-to-peer" is never fully serverless.
  • BitTorrent-style chunk sharing — used for large internal file distribution (Facebook and Twitter both built deployment systems on it) because it turns every receiving machine into a source.

35.4 Cluster membership and failure detection

  • Heartbeats — nodes report to a coordinator on a timer. Simple, and the coordinator becomes a bottleneck and an SPOF.
  • Gossip — each node periodically exchanges membership state with a few random peers; information spreads in O(log n) rounds. Decentralized, scales to thousands of nodes, and is how Cassandra, Consul, and Redis Cluster track membership.
  • Phi accrual failure detection — instead of a binary alive/dead timeout, output a suspicion level from the observed distribution of heartbeat intervals, so a slow network does not immediately look like a dead node.
  • Lease — a time-bounded grant ("you are the leader until T"). Self-expiring, so a partitioned holder stops acting without needing to be told.

36. Multi-tenancy, capacity, and cost

DEFINITION

Multi-tenancy is serving multiple independent customers (tenants) from shared infrastructure, with logical isolation between their data and usage rather than separate physical deployments per customer.

36.2 Capacity planning and autoscaling

  • Size for peak, not average, and know your peak's shape — a daily cycle, a weekly spike, or a launch event are three different plans.
  • Scale on the signal that actually correlates with work: queue depth or request concurrency, rarely CPU alone.
  • Autoscaling has lag — instance boot, warm-up, JIT, cache fill. Keep headroom (target ~60–70% utilization) so you survive the ramp.
  • Beware scaling into a bottleneck: doubling app servers when the database connection pool is the limit makes things worse.
  • Pre-warm before known events; scale down slowly and up quickly.

36.3 Cost levers, roughly in order of impact

  1. Egress bandwidth — CDN hit rate is usually the single biggest line item you control.
  2. Storage tiering and lifecycle rules — most data is never read after 30 days.
  3. Right-sizing and reserved or spot capacity for predictable and interruptible work.
  4. Reducing chattiness — a fan-out of 40 internal calls per page costs real money at scale.
  5. Retention policies on logs and metrics, which quietly become one of the largest bills in a mature system.

37. Recommendation and ML-backed systems

Feeds, search ranking, "people you may know", ads, and fraud checks all share one architecture. Knowing its shape lets you answer a class of questions that otherwise feels out of reach.

37.1 The serving pieces

  • Feature store — one definition of each feature, served online at low latency and offline for training. Exists to prevent training/serving skew, where the model was trained on features computed differently from the ones it sees in production.
  • Embeddings and vector search — represent users and items as vectors; retrieval becomes approximate nearest neighbour search (HNSW, IVF, product quantization) over millions of vectors in single-digit milliseconds. This is what a vector database provides.
  • Offline vs online — precompute what you can on a schedule (candidate pools, user embeddings), compute at request time only what depends on the moment.
  • Model serving — versioned models behind a service, with shadow deployment (send real traffic, discard the output) before a canary.
  • Cold start — new users and new items have no signal. Fall back to popularity, content-based similarity, or explicit onboarding preferences.

37.2 Experimentation

Any ranking change needs an A/B test: hash the user ID into buckets so assignment is stable and deterministic, run until you have statistical power, and watch guardrail metrics (latency, error rate, retention) alongside the target metric. Beware of interaction between concurrent experiments, novelty effects that fade, and metrics that improve engagement by making the product worse.

38. Testing and release confidence

DEFINITION

The testing pyramid describes the recommended mix of tests by level: many fast unit tests, fewer integration tests, and a small number of slow end-to-end tests — because cost and flakiness both rise as you move up the pyramid.

  • Dependency injection is what makes code testable — this is the practical payoff of the D in SOLID.
  • Shadow traffic — duplicate real requests to the new version and compare outputs without serving them. The safest way to validate a rewrite.
  • Test behaviour, not implementation. A test that breaks when you rename a private method is a liability.

39. Domain-driven design and application patterns

Section 25 covered object-level patterns. These are the ones that organize a whole service — the vocabulary that turns a pile of classes into an architecture.

39.1 DDD building blocks

  • Ubiquitous language — code uses the words the business uses. If they say "policy" and the class is called InsuranceRecord, every conversation costs a translation.
  • Entity — has identity that persists through change (a User is the same user after a rename).
  • Value object — defined entirely by its values, immutable, no identity (Money, DateRange, Address). Use these aggressively; they kill primitive obsession.
  • Aggregate — a cluster of objects treated as one unit, with a single aggregate root as the only entry point. Invariants hold inside the boundary; one transaction touches one aggregate. In distributed systems the aggregate is usually also your consistency and sharding boundary, which is why this concept earns its keep.
  • Repository — a collection-like interface for retrieving and saving aggregates, defined in the domain, implemented in infrastructure.
  • Domain service — behaviour that does not belong to any single entity (a transfer between two accounts).
  • Domain event — something meaningful that happened, published for other parts of the system to react to.
  • Bounded context — an explicit boundary within which a term has one meaning. "Customer" in billing and "customer" in support are different models; forcing them into one class is how god objects are born. Bounded contexts are the honest basis for splitting into services.

39.2 Layering and object roles

39.3 UI-side architecture patterns

  • MVC — controller handles input, model holds state and rules, view renders. The classic; controllers tend to swell.
  • MVP — the presenter holds all presentation logic and the view is passive, which makes the logic unit-testable.
  • MVVM — the view binds declaratively to a view-model that exposes observable state. The model behind most modern UI frameworks.
  • Common purpose: keep rendering out of the rules, and rules out of the rendering.

39.4 Dependency injection

// without DI: the class decides its own collaborators — untestable, unswappable

}

// constructor injection: dependencies are explicit, required, and immutable

    private final OrderRepository repo;
    private final Clock clock;                      // inject the clock, too —
    ReportService(OrderRepository repo, Clock clock) {   // otherwise time is untestable
        this.repo = repo; this.clock = clock;

Prefer constructor injection over setters or field injection: it makes missing dependencies a compile error rather than a null at runtime, and it makes the class's real dependency count visible — a constructor with nine parameters is telling you the class does too much.

40. Error handling, contracts, and code craft

DEFINITION

Defensive design means validating input at a system's boundary and converting it into types that make invalid states unrepresentable, so the code deeper inside can trust its own data.

40.1 Designing failure into the API

  • Validate at the boundary, then trust the data inward. Parse input into domain types once (a EmailAddress, not a String) so the inner layers cannot receive something invalid.
  • Exceptions vs result types — throw for genuinely exceptional, unrecoverable conditions; return an explicit result (Result<Order, PaymentError>) for expected outcomes like "card declined". Using exceptions for control flow hides the real paths through your code.
  • Fail fast on programming errors (null where impossible, invalid state) and fail soft on environmental ones (a timeout, a missing optional service).
  • Never swallow an exception. Catch what you can handle; wrap and rethrow what you cannot, preserving the cause.
  • Custom exception types per failure mode, so callers can branch without string-matching messages.
  • Error responses should carry a stable machine-readable code, a human message, and a correlation ID — the same ID that appears in your logs and traces.
  • Avoid returning null for collections (return empty) and prefer Optional or a nullable type at boundaries where absence is meaningful.

40.2 Clean code, compressed

  • Names should say what and why, never how. expiredSessions beats list2; a good name deletes the comment that would have explained it.
  • A function should do one thing at one level of abstraction. If you can extract a well-named method from the middle of it, it was doing two things.
  • Comments explain why, not what. A comment restating the code rots the moment the code changes.
  • Keep the happy path unindented: return early on guard conditions instead of nesting.
  • Minimize mutable state and the scope of every variable.
  • Boy scout rule — leave each file slightly better than you found it. Large refactors are rarely approved; small ones are never noticed.

40.3 Refactorings worth knowing by name

  • Extract method / extract class — the answer to a long function or a god object.
  • Introduce parameter object — the answer to a long parameter list.
  • Replace conditional with polymorphism — the answer to switch-on-type.
  • Replace magic number with named constant, and magic strings with enums.
  • Encapsulate collection — return an unmodifiable view, expose add/remove methods, keep the invariant inside.
  • Introduce null object — a do-nothing implementation that removes null checks scattered across callers.
  • Strangler fig — the pattern for replacing a legacy system: route new functionality to the new implementation while the old one shrinks, rather than a big-bang rewrite.

41. More high-level design case studies

41.1 Distributed unique ID generator

Requirements: unique, roughly time-sortable, 64-bit, no central bottleneck. Options: a database auto-increment (single point of failure), UUIDv4 (128-bit, no order, terrible as a clustered index key), a ticket server with ranges handed out in blocks, or Snowflake — 41 bits of millisecond timestamp, 10 bits of machine ID, 12 bits of per-millisecond sequence. That gives 4,096 IDs per machine per millisecond. Discuss clock drift: if the clock moves backwards, either wait it out or borrow from the sequence. Mention UUIDv7 as the modern time-ordered alternative.

41.2 Key–value store

The synthesis question — it touches nearly everything in Part 1. Partition with consistent hashing; replicate to the next N−1 nodes clockwise; tune consistency with W, R, and N; detect conflicts with vector clocks and resolve at the application; use gossip for membership and hinted handoff for temporarily-down nodes; anti-entropy via Merkle trees; storage as an LSM tree with Bloom filters per SSTable. If you can narrate that paragraph coherently, you have understood distributed systems.

41.3 Distributed cache

Client-side consistent hashing over a fleet of cache nodes, LRU per node, TTL with jitter, no replication of cache data (a miss is cheap), and careful handling of node loss: with consistent hashing only 1/N of keys go cold. Discuss whether to shard or replicate hot keys, and how invalidation reaches every node (pub/sub or versioned keys).

41.4 Collaborative document editing (Google Docs)

Two families of algorithm: operational transformation, where concurrent operations are transformed against each other to converge (what Google Docs uses; centralized and fiddly), and CRDTs, where the data type merges by construction (simpler reasoning, larger metadata). Around the algorithm: a WebSocket session per client, a per-document server that serializes operations, periodic snapshots so a new client does not replay the whole history, and presence/cursor broadcasting as a separate cheap channel.

41.5 Leaderboard / top-K

A Redis sorted set gives O(log n) updates and O(log n + k) range reads — sufficient up to a few million players per board. Beyond that, shard by score range or by region and merge, keep a per-shard local top-K, and compute global ranks approximately. For a stream (trending hashtags), use a count–min sketch plus a heap rather than exact counting. Decide up front whether "rank" must be exact: exact ranking of 100 million players in real time is a far harder and more expensive product than "top 100 plus your own rank".

41.6 Metrics and monitoring system

Agents push metrics to a collector; write into a time-series database with a rollup pipeline (raw for 24 h, 1-minute for a week, 1-hour for a year); query layer with downsampling; alerting engine evaluating rules on a schedule. The interesting constraints: enormous write rate with tiny values, high cardinality as the killer (every label combination is a new series), and the fact that the monitoring system must not depend on the system it monitors.

41.7 Distributed job scheduler

Store jobs with a next-run time; workers claim due jobs atomically (conditional update or a lease with a fencing token); heartbeat while running so a dead worker's job is reclaimed; exponential backoff and a DLQ for failures. Guarantee at-least-once and require idempotent jobs. Handle the thundering herd of "every job scheduled at midnight" with jitter, and support both cron-style recurrence and one-shot delayed tasks.

41.8 Ad click aggregator

A stream problem: millions of click events per second, aggregated into per-ad, per-minute counts that advertisers query. Kafka partitioned by ad ID, a stream processor doing windowed aggregation with watermarks for late events, results written to an OLAP store. Discuss exactly-once (idempotent writes keyed by window plus ad), reconciliation against a nightly batch job for billing correctness, and fraud filtering as a separate stage.

41.9 Digital wallet / payment ledger

Double-entry ledger as an append-only table; balances derived or maintained as a materialized projection; every operation carries an idempotency key; transfers between users are a single transaction inside one shard when possible, and a saga with reserve/commit/compensate when not. Strong consistency is non-negotiable, and reconciliation jobs are part of the design, not an afterthought.

41.10 Video conferencing (Zoom)

Small calls can be peer-to-peer mesh; beyond three or four participants you need a server. An SFU (selective forwarding unit) receives each participant's stream once and forwards it, doing no transcoding — cheap and the common choice. An MCU mixes streams into one, which is expensive but easy on clients. Add simulcast (each client sends several quality levels so the SFU can pick per receiver), jitter buffers, and a signalling service for session setup.

41.11 Proximity service (Yelp, "restaurants near me")

Geohash the venue locations and index the prefix, or use a quadtree when density varies wildly between Manhattan and a rural county. Query the cell containing the user plus its eight neighbours to avoid boundary misses, then filter by exact distance and rank. Venue data is read-heavy and almost static, so cache it hard; this is the opposite profile from the ride-hailing case, where positions change every few seconds.

41.12 Code deployment system

Build artifacts once, store them immutably, distribute to thousands of machines (peer-to-peer distribution beats a central download server at scale), then orchestrate a staged rollout: canary, region by region, with automated rollback triggered by error-rate and latency guardrails. The design pressure is distribution bandwidth and the correctness of the rollback path, which must be tested more carefully than the deploy path.

42. Questions worth asking about any design

About the requirements

  • Who are the users, and how many?
  • Which operations dominate — reads or writes?
  • What latency do users notice?
  • Where is stale data acceptable, and where is it not?
  • What must never be lost?
  • What is explicitly out of scope?

About the data

  • How much, growing how fast, kept how long?
  • What is the dominant access pattern?
  • What is the natural partition key?
  • What queries cross partitions, and can they be avoided?

About failure

  • What happens when this component dies?
  • What happens when it is slow rather than dead?
  • What happens when it comes back with stale state?
  • Which failures are silent?
  • Can every operation be safely retried?
  • How is the system restored after total data loss?

About the future

  • What breaks at 10× traffic? At 100×?
  • What is the next bottleneck after the current one?
  • Which decision here is hardest to reverse?
  • What are we paying for that we do not use?
THE LAST ONE IS THE MOST IMPORTANT

"Which decision is hardest to reverse?" Schema shape, shard key, and the public API contract are expensive to change later; caching layers, instance sizes, and internal service boundaries are cheap. Spend your design time in proportion.

43.6 What's genuinely reusable across all seven

The same five moves, every time

  • Cache the hot 20% aggressively (section 5) — every company above does this at the edge.
  • Move anything non-blocking off the request path (section 11) — encoding, ranking training, counters.
  • Denormalize the read model, reconcile async (sections 6.4, 41.6) — view counts, follower counts, feed entries.
  • Put a Strategy interface wherever business logic genuinely varies — pricing, ranking, ABR, DRM.
  • Choose CP for money and inventory, AP for everything else (section 9) — every company draws this line in the same place.

Where they actually differ

  • Hotstar/Netflix: CDN strategy and live-vs-VOD latency tolerance.
  • YouTube/Instagram: storage shape for the medium (Haystack for photos, chunked transcode for video).
  • Facebook: graph-shaped data needs a graph-shaped cache, not just a bigger SQL cluster.
  • Amazon/Flipkart: the atomic-decrement inventory problem under adversarial concurrency.
